\section{传输层}

网络层把分组送到目的主机，但主机上往往同时运行着浏览器、邮件客户端、DNS 解析器等多个进程。一个 IP 分组到达后，应该交给哪一个进程？这是传输层要回答的第一个问题。传输层把“主机到主机”的通信细化成“进程到进程”的通信，用端口号标识通信端点；在这个基础上，它还可以选择只做很薄的一层封装（UDP），或者用序号、确认、重传、窗口和拥塞控制搭出一套可靠的字节流服务（TCP）。本章沿着“端口与复用分用 $\to$ UDP $\to$ 可靠传输的通用机制 $\to$ TCP 的可靠传输、流量控制、拥塞控制与连接管理”这条线展开。

\subsection{端口、套接字与复用分用}

一台主机只有一个（或几个）IP 地址，却可能同时运行几十个网络进程。传输层给每个进程分配一个 16 位的\textbf{端口号}（0--65535），IP 地址加端口号就构成一个\textbf{套接字地址}。发送数据时，多个进程的数据被传输层汇聚后交给 IP 层，这叫\textbf{复用}（multiplexing）；接收数据时，传输层根据端口号把数据交给正确的进程，这叫\textbf{分用}（demultiplexing）。

图里最值得注意的是：IP 层只负责把数据报送到主机 B，真正的“分拣”发生在传输层。接收方看到目的端口 80，就把数据交给 Web 服务器；看到 53，就交给 DNS 服务器。端口号只在本地有意义，不同主机上的同一个端口号互不冲突。

端口号分为三段：0--1023 是\textbf{知名端口}，由 IANA 分配给标准服务，例如 HTTP 80、HTTPS 443、DNS 53、SMTP 25、POP3 110、FTP 21 和 20、Telnet 23；1024--49151 是\textbf{注册端口}；49152--65535 是\textbf{动态端口}，客户端通常临时申请一个这样的端口。408 选择题里常见的陷阱是“客户端端口必须大于 1024”之类的绝对化说法——标准服务也可以使用动态端口，关键看进程是否绑定。

仅有“IP 地址 + 端口”还不够区分 TCP 连接。一条 TCP 连接由\textbf{源 IP、源端口、目的 IP、目的端口}四元组唯一标识。因此，同一台 Web 服务器可以在本地 80 端口上同时服务成千上万个客户：它们的四元组不同。UDP 的分用通常只看目的端口（以及绑定时的本地 IP），所以一个 UDP 端口上的数据报可能来自很多不同客户。

\subsection{UDP：只加一层薄薄的信封}

UDP（User Datagram Protocol）的设计目标是把事情做少。它在 IP 之上只增加了端口号和校验和，提供\textbf{无连接、不可靠、面向报文}的传输服务。发送前不需要握手，发送后不等待确认；数据报可能丢失、重复、乱序，UDP 本身不负责恢复。也正因为如此，UDP 首部只有 8 字节，发送方不需要维护连接状态，适合 DNS、DHCP、TFTP、SNMP、实时音视频这类“宁可丢一点，也不要等”的应用。

“面向报文”是 UDP 最容易被误解的性质。应用层每调用一次 \texttt{sendto}，UDP 就把它封装成一个独立的数据报，既不合并也不拆分；接收方每调用一次 \texttt{recvfrom}，最多取走一个完整的数据报。若接收缓冲区小于数据报长度，多余部分会被截断丢弃，而不会像 TCP 那样留在缓冲区里等下一次读取。IP 层在下面可能会分片，但那是 IP 层的事，分片在到达目的主机后由 IP 层重组，UDP 看到的仍然是一个完整报文。

首部四个字段各 16 位。\textbf{长度}字段包含 8 字节首部和数据部分，最小值是 8（没有数据）。16 位长度字段理论上允许 65535 字节的 UDP 数据报，但 IPv4 总长度字段也只有 16 位，减去至少 20 字节 IP 首部和 8 字节 UDP 首部后，UDP 数据部分最大为 65507 字节；若 IP 首部带选项，还要更小。

\textbf{校验和}覆盖三部分：伪首部、UDP 首部和 UDP 数据。伪首部包含源 IP、目的 IP、一个全 0 字节、协议号 17 和 UDP 长度，共 12 字节。计算时先把校验和字段置 0，若数据部分为奇数字节，末尾临时补一个全 0 字节（补的字节不传输、也不计入长度），然后按 16 位字做\textbf{二进制反码求和}：相加时若最高位产生进位，就把进位加回最低位；最后把结果取反，填入校验和字段。若计算结果为 0，则填入全 1（\texttt{0xFFFF}），因为反码表示中全 0 与全 1 都表示“零”。

IPv4 中 UDP 校验和是\textbf{可选}的：校验和字段为 0 表示发送方没有计算校验和。IPv6 中 UDP 校验和是强制性的。408 题目若给出“校验和字段为 0”，要按“未计算”处理，而不是按“校验结果为 0”处理。

UDP 不提供流量控制，也不提供拥塞控制。发送方可以按应用产生的速率直接往网络里灌数据；网络拥塞时，UDP 不会自动减速。可靠性只能由应用层自己补，例如 DNS 客户端在超时后重发查询，实时音视频则常常直接丢弃迟到数据。

\subsection{可靠传输：从停等到滑动窗口}

IP 层提供的是“尽最大努力”服务，分组可能出错、丢失、重复或乱序。要在这样的基础上实现可靠传输，需要一套基本工具：\textbf{校验和}发现比特错误，\textbf{确认}（ACK）告诉发送方哪些数据已经收到，\textbf{定时器}处理确认丢失，\textbf{序号}处理重复和乱序。停等、后退 N 帧（GBN）和选择重传（SR）是三种最典型的协议，它们的关系是“窗口从 1 到 N、接收方从只收到缓存”的逐步放松。

\subsubsection{停等协议与链路利用率}

停等协议（Stop-and-Wait）最简单：发送方发出一帧后停下来，等收到该帧的确认再发下一帧。如果定时器超时还没收到确认，就重传。接收方收到正确帧后回 ACK，收到重复帧则丢弃并重发 ACK。用 1 位序号就足以让接收方区分“新帧”和“上一帧的重复”：发送方在 0、1 之间交替，接收方期望的序号也随之交替。

停等协议的问题是\textbf{链路利用率低}。设帧的发送时延为 $T_D$，往返时延为 RTT，确认帧的发送时延为 $T_A$，则
\[
U=\frac{T_D}{T_D+\mathrm{RTT}+T_A}.
\]
分母里的 RTT 主要由传播时延和中间节点处理时延构成。举个例子：链路速率 1 Gbps，帧长 1000 B，RTT 为 10 ms。帧的发送时延
\[
T_D=\frac{1000\times 8}{10^9}=8\ \mu\mathrm{s},
\]
而 RTT 是 10 ms，约是 $T_D$ 的 1250 倍，于是
\[
U\approx\frac{8\ \mu\mathrm{s}}{10\ \mathrm{ms}+8\ \mu\mathrm{s}}\approx 0.08\%.
\]
也就是说，发送方 99.9\% 的时间在等确认，链路几乎空闲。

\subsubsection{后退 N 帧（GBN）}

GBN 的发送方维护一个长度为 $W$ 的\textbf{发送窗口}，窗口内的序号是“已发送但还没被确认”和“还可以发送”的范围。接收方的窗口长度只有 1：它只按序接收，期望的序号是 \texttt{rcv\_base}。收到序号等于 \texttt{rcv\_base} 的帧，就交付给上层、把 \texttt{rcv\_base} 加 1，并回一个累计确认；收到序号不等于 \texttt{rcv\_base} 的帧，即使内容正确也直接丢弃，并重复回上一次的确认。

发送方只给窗口内最老的未确认帧设置一个定时器。收到确认号 $n$ 时，表示 $n$ 及之前的帧都已被正确接收，窗口可以滑到 $n+1$。如果最老帧超时，发送方把窗口内所有已发送但未确认的帧全部重传——这就是“后退 N 帧”名字的来源。

GBN 的接收窗口为 1，所以实现简单、接收方不需要缓存乱序帧；代价是一次丢失可能导致整个窗口重传。链路误码率低时，这种浪费可以接受；误码率高时，GBN 的效率会明显下降。

GBN 的序号位数 $n$ 和窗口长度 $W$ 必须满足
\[
W\le 2^n-1.
\]
为什么不能取 $W=2^n$？设 $n=2$，序号为 0--3，窗口取 4。发送方连续发出 0、1、2、3，四帧都正确到达，接收方回 ACK 0--ACK 3。假如所有 ACK 都丢失，发送方超时后重传 0。此时接收方已经收完 0--3，期望的序号回到下一轮的 0；重传的 0 正好等于期望值，于是被当成新帧接收，上层收到重复数据。取 $W=2^n-1$ 时，例如 $n=2$、$W=3$，接收方收完 0、1、2 后期望 3；重传的 0 不等于 3，会被丢弃，不会产生重复。

\subsubsection{选择重传（SR）}

SR 把接收窗口也扩大到 $W$：接收方可以接收并缓存窗口内的乱序帧，对每一帧单独回确认；当缺失的帧到达、把空洞补上后，再把缓存中连续的帧一起交付给上层。发送方为每个未确认帧维护逻辑定时器，哪一帧超时就只重传哪一帧，而不是重传整个窗口。

图中发送方窗口从 6 开始，7--13 已发送且被接收方缓存，只有 6 缺失。发送方超时后只重传 6；接收方收到 6 后，把 6--13 一起交付，窗口滑到 14。与 GBN 相比，SR 避免了重传已经正确到达的 7--13，但接收方要维护缓存和乱序帧的确认信息，发送方也要为每帧维护定时器，复杂度更高。

SR 的窗口长度必须满足
\[
W\le 2^{n-1}.
\]
原因是发送窗口和接收窗口不能“重叠”到让旧帧和新帧混淆。设 $n=3$，序号 0--7，若取 $W=5>4$。发送方发出 0--4，接收方全部收到并回 ACK，但 ACK 全丢；接收方窗口滑到 5、6、7、0、1，期望下一轮的 5。发送方超时后重传 0--4，其中 0、1 正好落在接收方的新窗口内，接收方会把它们当成新数据接收，造成重复。取 $W\le 2^{n-1}$ 时，发送方最多重传 $W$ 个旧帧，而接收方窗口已经滑过至少 $W$ 个序号，旧帧不会落入新窗口。

TCP 并不是纯粹的 GBN 或 SR。它使用累计确认，正常情况下像 GBN；但它有快速重传机制，收到 3 个重复 ACK 就立即重传缺失段，而不必等超时；还可以通过 SACK 选项告诉发送方哪些段已经收到，从而只重传真正缺失的部分。可以把它看成“以 GBN 为主、在丢包时借用 SR 思想”的混合方案。

\subsection{TCP 报文段与可靠传输}

TCP（Transmission Control Protocol）提供面向连接、可靠、全双工、面向字节流的传输服务。它把应用层交下来的数据看成没有边界的字节流，为每个字节编号，用确认号告诉对方“我下一个想收哪个字节”。为了在 IP 之上实现可靠传输，TCP 使用校验和、序号、确认、超时重传和滑动窗口；为了不让发送方压垮接收方或网络，它又加入流量控制和拥塞控制。

\subsubsection{首部格式}

TCP 报文段首部固定部分 20 字节，加上最多 40 字节选项，最长 60 字节。

几个字段的含义需要记牢。\textbf{数据偏移}占 4 位，单位是 4 字节，所以最小值为 5（$5\times4=20$ 字节），最大值为 15（60 字节）。\textbf{保留}字段目前一般置 0。六个标志位中，URG 表示紧急指针有效，ACK 表示确认号有效，PSH 表示请求接收方尽快交付，RST 用于复位连接，SYN 用于建立连接，FIN 用于释放连接。\textbf{窗口}字段是接收窗口 rwnd，单位字节，16 位最大 65535；若使用窗口扩大选项，实际窗口可以按协商的移位值左移。

\textbf{校验和}的计算方法与 UDP 类似，伪首部中的协议号改为 6，长度改为 TCP 长度（首部 + 数据）。TCP 校验和是强制性的。

TCP 的 \textbf{MSS}（Maximum Segment Size）指数据部分的最大长度，不包括 TCP 首部。以太网 MTU 为 1500 B 时，减去 20 B IP 首部和 20 B TCP 首部，MSS 通常取 1460 B；MSS 在连接建立时由双方协商。

\subsubsection{序号、确认号与字节流}

TCP 的序号不是“第几个报文段”，而是“数据部分第一个字节在字节流中的编号”。假设初始序号 ISN 为 2001，发送方发送 1000 字节，则本报文段的序号是 2001，下一个报文段的序号是 3001；接收方正确收到后，回确认号 3001，表示“2001--3000 都收到了，下一个想收 3001”。

TCP 是全双工的，两个方向各自维护序号和确认号。连接建立时，双方通过 SYN 交换初始序号；SYN 本身消耗一个序号，所以客户端发 SYN（seq=$x$）后，服务器的确认号是 $x+1$。FIN 也消耗一个序号。纯粹的 ACK 报文段如果不携带数据，不消耗序号。

TCP 是面向字节流的，这意味着它不保留应用层的报文边界。应用层三次写入 100 字节，接收方可能一次读到 300 字节，也可能分三次读到 100 字节；应用层必须自己按协议格式解析边界。这一点与 UDP 的“一次发送对应一个数据报”正好相反。

\subsubsection{超时重传与 RTT 估计}

TCP 为发送出去但尚未确认的数据设置定时器。超时时间 RTO 不能拍脑袋定：太小会频繁误重传，太大会在真正丢包时等待过久。TCP 用往返时延的指数加权移动平均来估计 RTT。记 $E$ 为平滑后的 RTT 估计，$D$ 为 RTT 偏差的估计，$S$ 为本次测量得到的 SampleRTT，则
\begin{align}
E_{\mathrm{new}}&=(1-\alpha)E_{\mathrm{old}}+\alpha S, & \alpha&=\frac18,\\
D_{\mathrm{new}}&=(1-\beta)D_{\mathrm{old}}+\beta\lvert S-E_{\mathrm{old}}\rvert, & \beta&=\frac14,\\
\mathrm{RTO}&=E_{\mathrm{new}}+4D_{\mathrm{new}}. &&
\end{align}
第一式让 $E$ 平滑地跟随新样本，第二式估计 RTT 的波动；RTO 在平均值上再加 4 倍偏差，给波动留出余量。举个数值例子：设 $E_{\mathrm{old}}=100$ ms，$D_{\mathrm{old}}=10$ ms，本次 $S=120$ ms，则
\[
E_{\mathrm{new}}=0.875\times100+0.125\times120=102.5\ \mathrm{ms},
\]
\[
D_{\mathrm{new}}=0.75\times10+0.25\times|120-100|=12.5\ \mathrm{ms},
\]
\[
\mathrm{RTO}=102.5+4\times12.5=152.5\ \mathrm{ms}.
\]
工程实现还会给 RTO 设置上下限，初始 RTO 通常取 1 秒左右；408 计算题一般按题目给出的初值和公式计算。

这里有一个容易被忽略的问题：如果报文段被重传过，那么收到的 ACK 到底是对原始发送的确认，还是对重传副本的确认？发送方无法区分。因此 \textbf{Karn 算法}规定：\textbf{重传过的报文段不参与 RTT 样本的计算}；同时，超时后 RTO 按指数退避（每超时一次翻倍），直到收到一个没有歧义的新数据确认，再恢复正常的 RTT 估计。这样避免把“重传后的 ACK”误当成“原始发送的 ACK”，把 RTT 估计得过大或过小。

\subsection{TCP 的流量控制}

流量控制解决的是“发送方太快，接收方缓冲区放不下”的问题。接收方在 TCP 首部的窗口字段中告诉发送方：从确认号开始，我还能接收多少字节。这个值叫\textbf{接收窗口} rwnd。发送方的实际发送窗口不能超过 rwnd，也不能超过拥塞窗口 cwnd，因此
\[
\text{发送窗口}=\min(\mathrm{rwnd},\mathrm{cwnd}).
\]
流量控制是端到端的，只考虑接收方的处理能力；拥塞控制考虑的是整个网络，二者共同限制发送速率。

图中的确认号是 8001，接收方通告 rwnd=4000 B，所以窗口覆盖 8001--12000。发送方已经有 1.5 KB 在途（8001--9500），因此还能发送 2.5 KB（9501--12000）。如果发送方还有更多数据，只能等新的 ACK 把窗口往前推。

当接收方缓冲区满时，它通告 rwnd=0。发送方暂停发送，但不能就此认为连接死了：它会启动\textbf{坚持定时器}（persist timer），定期发送\textbf{零窗口探测报文}，接收方收到后回复当前窗口大小。这样即使窗口更新报文丢失，双方也不会互相等待而死锁。

窗口字段只有 16 位，最大 65535 字节。在高带宽时延积较大的链路上，这个窗口太小，会限制吞吐量。TCP 的\textbf{窗口扩大选项}允许双方在建立连接时协商一个移位值，把窗口字段左移若干位，从而表示更大的窗口。

还有一个细节叫\textbf{糊涂窗口综合征}（Silly Window Syndrome）：接收方每次只腾出几个字节就通告一个很小的窗口，发送方于是发出大量首部占主导的小段，效率极低。解决办法分两头：接收方采用 Clark 算法，等到缓冲区有足够空间（例如能放下一个 MSS 或缓冲区的一半）再通告非零窗口；发送方采用 Nagle 算法，在还有未确认数据时先把小段攒起来，等到凑满 MSS 或收到 ACK 再发。Nagle 算法和延迟确认一起使用时，可能让交互式应用多等几十毫秒，所以有些实时应用会关闭 Nagle。

\subsection{TCP 的拥塞控制}

流量控制防止压垮接收方，拥塞控制防止压垮网络。发送方维护一个\textbf{拥塞窗口} cwnd，表示在不知道网络当前能承受多少之前，自己允许有多少数据在途。cwnd 是发送方根据丢包事件推测出来的，不是接收方通告的。真正能发多少仍然取 $\min(\mathrm{rwnd},\mathrm{cwnd})$。cwnd 和 ssthresh 的单位可以是 MSS 或字节，同一道题里要保持一致；408 题目常用 MSS 为单位。

TCP 拥塞控制有四个经典算法：慢开始、拥塞避免、快重传、快恢复。它们围绕两个变量工作：cwnd 和\textbf{慢开始门限} ssthresh。

\textbf{慢开始}从很小的 cwnd 开始（教材通常取 1 MSS）。每收到一个对新数据的 ACK，cwnd 增加 1 MSS；如果所有 ACK 都按时到达，那么每经过一个 RTT，cwnd 翻一倍：1、2、4、8、16……所以“慢开始”其实不慢，它是指数增长，只是起点小。当 cwnd 达到 ssthresh 时，转入拥塞避免。

\textbf{拥塞避免}把指数增长改成线性增长：每经过一个 RTT，cwnd 增加 1 MSS。按单个 ACK 计算，增量约为 $\mathrm{MSS}^2/\mathrm{cwnd}$，累加一个 RTT 正好约 1 MSS。这个阶段增长慢，但更稳，通常称为“加法增大”（Additive Increase）。

发生丢包时，TCP 用两种方式判断，处理方式不同：

\begin{itemize}
  \item \textbf{超时}：发送方等不到确认，说明情况可能很严重。此时令
  \[
  \mathrm{ssthresh}=\max\left(\frac{\mathrm{cwnd}}{2},\,2\ \mathrm{MSS}\right),\qquad
  \mathrm{cwnd}=1\ \mathrm{MSS},
  \]
  然后重新进入慢开始。这就是“乘法减小”（Multiplicative Decrease）。
  \item \textbf{3 个重复 ACK}：发送方连续收到 3 个重复 ACK，说明缺失段之后的报文段还在到达，网络并没有完全堵死。此时执行\textbf{快重传}，立即重传缺失段，不必等超时；同时令
  \[
  \mathrm{ssthresh}=\frac{\mathrm{cwnd}}{2},\qquad
  \mathrm{cwnd}=\mathrm{ssthresh},
  \]
  然后直接进入拥塞避免。这个过程叫\textbf{快恢复}：窗口减半，但不回到 1，因为网络显然还在交付数据。
\end{itemize}

这里的“3 个重复 ACK”是指：在原本的 ACK 之后，又收到 3 个确认号相同、且没有确认新数据的 ACK。发送方据此推断，缺失段之后至少有三个报文段到达了接收方。

\begin{attention}
\textbf{本章统一采用的教材化规则。} 408 教材和多数题目对快恢复做了简化：收到 3 个重复 ACK 时，直接把 cwnd 置为减半后的 ssthresh，然后进入拥塞避免。真正的 TCP Reno 会把 cwnd 临时置为 $\mathrm{ssthresh}+3$ MSS，每多一个重复 ACK 再膨胀 1 MSS，直到收到确认新数据的 ACK 才收缩回 ssthresh。两种写法在考试中可能给出不同数值。本章习题统一使用简化规则；只有题目明确写“TCP Reno 快恢复”时，才使用 $+3$ 的细节。超时处理则统一取 $\mathrm{ssthresh}=\max(\mathrm{cwnd}/2,2\ \mathrm{MSS})$，除法按题目要求取整，未说明时向下取整到整数 MSS。
\end{attention}

还有一个容易出错的细节：慢开始阶段每个 RTT 翻倍，如果翻倍后超过了 ssthresh，\textbf{不截断}。例如 ssthresh=10 MSS，cwnd 从 8 MSS 翻到 16 MSS，这一轮仍然按慢开始完成；下一轮才转入拥塞避免。408 的填表题经常在这里设坑。

这张图把一次完整的拥塞事件画了出来。初始 ssthresh=16 MSS：第 1--5 轮 cwnd 按 1、2、4、8、16 指数上升，第 5 轮到达门限；第 6--9 轮转入拥塞避免，每轮加 1，到 20 MSS 时发生超时。超时后 ssthresh 减半为 10 MSS，cwnd 跌回 1 MSS，重新慢开始。第 10--14 轮又按 1、2、4、8、16 上升；注意第 14 轮从 8 翻到 16，越过了新的门限 10，但没有被截断。第 15 轮起进入拥塞避免，每轮加 1，直到 24 MSS 时收到 3 个重复 ACK。此时 ssthresh 减半为 12 MSS，cwnd 置为 12 MSS，直接进入拥塞避免，所以曲线上只下降到 12，而不是跌到 1。

对比超时和 3 个重复 ACK 这两处下落，可以看到：超时是“跌到 1 再指数爬升”，3 个重复 ACK 是“减半后线性爬升”。这就是 TCP 拥塞控制最典型的锯齿形。图中的 ssthresh 用阶梯虚线表示：16 $\to$ 10 $\to$ 12，每次都在丢包事件发生时更新。

拥塞控制的效果是整个网络收益：所有 TCP 连接在丢包时都减半，在正常时慢慢加一，总体呈现“加法增大、乘法减小”的 AIMD 行为。它不能保证公平，但能在没有集中调度的情况下让网络大致稳定运行。

\subsection{连接管理}

TCP 是面向连接的，通信前要建立连接，通信后要释放连接。连接建立和释放的过程不仅是“打招呼”，还要交换初始序号、确认双方的收发能力，并处理旧报文段和异常情况。

\subsubsection{三次握手}

三次握手的过程如下：

\begin{enumerate}
  \item 客户端发送 \texttt{SYN=1, seq=x}，进入 \texttt{SYN-SENT} 状态。这个报文段不携带数据，但消耗一个序号 $x$。
  \item 服务器收到后，回复 \texttt{SYN=1, ACK=1, seq=y, ack=x+1}，进入 \texttt{SYN-RCVD} 状态。它确认了客户端的 $x$，同时告诉客户端自己的初始序号是 $y$。
  \item 客户端收到后，发送 \texttt{ACK=1, seq=x+1, ack=y+1}，进入 \texttt{ESTABLISHED} 状态。服务器收到这个 ACK 后也进入 \texttt{ESTABLISHED}。
\end{enumerate}

为什么需要三次，而不是两次？核心原因是防止\textbf{已失效的连接请求}突然到达服务器。假设客户端很早以前发出的一个 SYN 在网络中滞留，客户端已经放弃并重新发起连接；如果只有两次握手，这个迟到的 SYN 到达服务器后，服务器会直接认为连接建立并分配资源，而客户端根本不会使用它，资源就被浪费了。三次握手中，服务器收到旧 SYN 后回 SYN+ACK，客户端看到不认识的确认号，会回 RST 拒绝，服务器就不会建立连接。

三次握手还让双方都确认了对方的发送和接收能力：客户端从 SYN+ACK 知道服务器能收也能发，服务器从第三次 ACK 知道客户端能收。同时，双方交换了初始序号，为后续的可靠传输打下基础。

\subsubsection{四次挥手与 TIME-WAIT}

TCP 是全双工的，两个方向要分别关闭，所以释放连接通常需要四次报文交换：

\begin{enumerate}
  \item 客户端发送 \texttt{FIN=1, seq=u}，进入 \texttt{FIN-WAIT-1}。FIN 消耗一个序号。
  \item 服务器回复 \texttt{ACK=1, ack=u+1}，进入 \texttt{CLOSE-WAIT}。客户端收到后进入 \texttt{FIN-WAIT-2}。此时客户端到服务器方向已经关闭，但服务器还可以继续发送数据，这叫\textbf{半关闭}。
  \item 服务器把剩余数据发完后，发送 \texttt{FIN=1, ACK=1, seq=w, ack=u+1}，进入 \texttt{LAST-ACK}。
  \item 客户端回复 \texttt{ACK=1, ack=w+1}，进入 \texttt{TIME-WAIT}，等待 2MSL 后进入 \texttt{CLOSED}。服务器收到这个 ACK 后立即进入 \texttt{CLOSED}。
\end{enumerate}

图中服务器收到 FIN 后进入 \texttt{CLOSE-WAIT}，它还可以把剩余数据发完（虚线箭头），然后才发自己的 FIN。客户端回复最后一个 ACK 后进入 \texttt{TIME-WAIT}，等待 2MSL 才真正关闭。

TIME-WAIT 要等 2MSL，原因有两个。第一，最后一个 ACK 可能丢失；如果服务器没收到 ACK，会重发 FIN，客户端在 TIME-WAIT 期间还能再回一次 ACK。如果客户端发完 ACK 就立即关闭，服务器重发的 FIN 就没人理，服务器会一直停在 \texttt{LAST-ACK}。第二，等待 2MSL 可以让本次连接产生的所有旧报文段在网络中消失，避免它们干扰下一个使用相同四元组的新连接。MSL 是报文段最大生存时间，教材常取 2 分钟，因此 2MSL 约为 4 分钟；具体实现可能更短。

TCP 的完整状态比上面两条路径多。建立连接涉及 \texttt{CLOSED}、\texttt{LISTEN}、\texttt{SYN-SENT}、\texttt{SYN-RCVD}、\texttt{ESTABLISHED}；关闭连接涉及 \texttt{FIN-WAIT-1}、\texttt{FIN-WAIT-2}、\texttt{CLOSE-WAIT}、\texttt{LAST-ACK}、\texttt{TIME-WAIT}。如果双方同时关闭，还会出现 \texttt{CLOSING} 状态；408 选择题偶尔考状态名称，但重点是主动关闭方和被动关闭方各自经过哪些状态。

连接管理还要注意异常情况。如果收到不匹配的报文段，或者端口没有进程监听，主机可能回 RST 复位连接。SYN 洪泛攻击利用大量伪造源地址的 SYN 把服务器的半连接队列占满，使正常客户无法完成三次握手；常见的防御手段包括 SYN cookie、缩短半连接超时、限制半连接数量等。

\subsection{把本章串起来}

传输层的核心问题是“进程到进程”的交付，端口号负责复用和分用。UDP 只做端口和校验，保留报文边界，不保证可靠，也不做流量控制和拥塞控制；它的简单换来了低开销和低时延。TCP 在 IP 之上用序号、确认、定时器和滑动窗口实现可靠字节流：序号按字节编号，确认号是期望收到的下一个字节；超时重传用 RTT 估计和 Karn 算法确定时机；流量控制用 rwnd 防止压垮接收方；拥塞控制用 cwnd 和 ssthresh 防止压垮网络；连接管理用三次握手和四次挥手建立、释放连接。

可靠传输的通用机制可以单独拿出来比较：停等协议窗口为 1，链路利用率低；GBN 用接收窗口 1 和累计确认换取简单，但一次丢失会重传整个窗口；SR 用接收缓存和逐帧确认换取效率，但实现复杂。GBN 的窗口上限是 $2^n-1$，SR 是 $2^{n-1}$，这两个不等式来自“序号空间必须大于窗口，否则旧帧会冒充新帧”。
