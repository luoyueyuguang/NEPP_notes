\section{进程管理}

同一份 \texttt{ls} 程序，在三个终端里各运行一次，系统里就有三个进程。程序只是磁盘上的静态文件，进程则是它在某台机器上的一次执行：有自己的程序计数器、寄存器、栈和地址空间。操作系统管理 CPU，实际上就是管理这些进程——让谁上 CPU、什么时候换下来、多个进程怎样共享资源而不互相破坏。本章围绕这条主线展开。

\subsection{程序与进程}

\begin{mydef}{进程与进程映像}{proc-def}
程序（program）是存放在磁盘上的指令和数据集合，是被动的。进程（process）是程序的一次执行实例，是动态的，拥有运行现场。进程在内存中的那份实体称为\textbf{进程映像}（process image），通常包括代码段、数据段、堆、栈，以及内核中的进程控制块（PCB）。
\end{mydef}

同一份程序可以对应多个进程，每个进程的代码段可以共享同一份只读页面，但数据、堆、栈和寄存器现场各自独立。图~2-1 画出了一个进程映像的典型布局：代码段在低地址，栈在高地址并向低地址增长，堆向高地址增长；PCB 不在用户地址空间里，而是放在内核区，由操作系统直接管理。

图里左边是内核中的 PCB，右边是用户态地址空间的四个主要区域。PCB 记录“这个进程是谁、现在什么状态、现场在哪里”，页表基址把它和右边的地址空间连起来。进程切换时，操作系统把当前 CPU 的 PC、寄存器和栈指针写回 PCB，再读出下一个进程的 PCB；如果两个进程不属于同一地址空间，还要切换页表。

PCB 是操作系统感知进程存在的唯一标志。创建进程的本质是建立 PCB 并分配地址空间；撤销进程的本质是回收它占用的资源并删除 PCB。PCB 通常包含：进程标识（PID、父进程 PID、用户 ID）、处理机状态（通用寄存器、PC、PSW、栈指针）、调度信息（状态、优先级、等待时间）、内存管理信息（页表指针、基址/限长）、I/O 状态（打开文件表、设备、缓冲区）。

\paragraph{创建与终止。} 类 UNIX 系统用 \texttt{fork()} 创建子进程：调用一次，返回两次——父进程得到子进程的 PID，子进程得到 0，两者从同一条语句继续执行。子进程先复制父进程的地址空间（写时复制），随后通常调用 \texttt{exec()} 用新程序替换整个映像。子进程先退出而父进程还没 \texttt{wait()} 时，子进程变成\textbf{僵尸}（zombie），PCB 和 PID 仍占着；父进程先退出时，子进程成为\textbf{孤儿}，由 \texttt{init} 或 \texttt{systemd} 收养。

进程控制操作（创建、终止、阻塞、唤醒、挂起、激活）必须是\textbf{原语}：执行过程中不能被中断，否则 PCB 队列或资源计数可能处于半更新状态。实现上常用关中断或内核锁保证原子性。

\subsection{进程状态：PCB 在队列间移动}

进程并不是一直都能运行。它可能正在等 CPU，也可能在等磁盘、等键盘、等另一个进程释放信号量。把“为什么现在不能运行”区分开，就有了进程状态。图~2-2 是常见的五状态模型。

每条边对应一个具体事件。创建完成后进程进入就绪态；调度程序从就绪队列选中它，才进入运行态。运行态的时间片用完，或者被更高优先级的进程抢占，退回就绪态——注意它并没有在等什么事件，只是暂时失去 CPU。运行态执行了 \texttt{read()} 之类的系统调用，或者执行 $P$ 操作发现资源不够，就主动进入阻塞态。阻塞的原因消失（磁盘中断到达、信号量被 $V$），进程回到就绪态，而不是直接回到运行态。

两条“不存在的边”是考试常考点。就绪态没有 CPU，无法执行指令，所以不可能自己发起 I/O 或 $P$ 操作进入阻塞态；阻塞态不在就绪队列里，调度程序根本不会选它，所以不可能直接进入运行态。运行 $\to$ 就绪与运行 $\to$ 阻塞也是两回事：前者是被剥夺 CPU，后者是主动等待事件。

内存紧张时，操作系统还可能把整个进程换到外存，形成\textbf{就绪挂起}和\textbf{阻塞挂起}两个状态，这就是七状态模型。挂起的进程即使等待的事件发生，也要先被“激活”换回内存，才能参与调度。中级调度负责换出和换入，下一节还会提到。

状态变化最终落实为 PCB 在队列之间的移动：就绪队列放着所有能运行的 PCB，每个设备（或每类事件）有一个等待队列。进程映像通常留在内存不动，除非被挂起。调度程序做的事，就是从就绪队列取下一个 PCB，恢复它的现场。

右图是三种映射。多对一把多个用户线程映射到一个内核线程：切换在用户态完成，很快；但一个线程执行阻塞系统调用，内核看到的是整个进程阻塞，其他线程也动不了，而且同一时刻只能用一个 CPU 核。一对一把每个用户线程对应一个内核线程：一个线程阻塞不影响同进程其他线程，也能真正并行；代价是创建和切换都要陷入内核。多对多把多个用户线程复用到较少的内核线程上，兼顾并行和开销，但实现最复杂。

用户级线程由线程库管理，内核不可见；内核级线程由内核调度。判断“一个线程阻塞会不会拖住整个进程”“能不能在多核上并行”时，必须先看采用的是哪种映射，不能只背“线程比进程轻”这一句话。

共享存储最快，因为两个进程的页表指向同一组物理页，读写就是普通的内存访问；代价是没有任何天然的互斥，双方必须自己用信号量或互斥量保护共享数据。消息传递通过 \texttt{send}/\texttt{receive} 交换消息，数据要从发送方复制到内核、再复制到接收方，开销更大，但隔离性好，也适合跨机器通信。消息传递可以分直接通信（指定对方进程）和间接通信（通过邮箱），还可以分阻塞和非阻塞：阻塞发送要等消息被取走或放进缓冲区，非阻塞发送放得下就返回。

管道是内核中的字节流缓冲区，\texttt{pipe()} 返回读端和写端两个文件描述符。普通管道是半双工的，通常只能用于有亲缘关系的进程；命名管道（FIFO）有文件名，可以让无亲缘关系的进程打开。管道为空时，读操作阻塞（只要还有写端打开）；管道满时，写操作阻塞。管道不保留消息边界，写入的多个字节可能被读端分几次读走。

\end{center}

高级调度（作业调度）决定哪些外存作业被装入内存，频率最低，批处理系统才有；分时和实时系统通常没有这一级。中级调度（内存调度）在内存紧张时把进程换出到外存，条件合适再换入，对应挂起和激活。低级调度（进程调度）从就绪队列选一个进程上 CPU，频率最高，任何操作系统都必须有。图里还可以看到，阻塞队列和就绪队列不是一回事：进程等 I/O 时在阻塞队列，事件发生后 PCB 才被移到就绪队列。

需要调度的情况有：进程运行结束；进程主动阻塞；时间片用完；更高优先级进程到达；中断处理结束返回时发现有更高优先级进程就绪。中断处理程序内部通常不切换进程，调度发生在中断返回之前；内核临界区或原子操作过程中也不调度，否则队列和计数器可能被破坏。

\paragraph{调度指标。} 设进程 $i$ 的到达时间为 $A_i$，运行时间为 $B_i$，完成时间为 $C_i$，第一次获得 CPU 的时刻为 $F_i$。

\begin{formula}{调度指标}{sched-metrics}
\[
T_i=C_i-A_i,\qquad W_i=T_i-B_i,\qquad
\text{带权周转}=\frac{T_i}{B_i},\qquad
\text{响应时间}=F_i-A_i.
\]
平均周转时间为 $\frac1n\sum_i T_i$，平均带权周转为 $\frac1n\sum_i T_i/B_i$。等待时间只统计进程在就绪队列中等待 CPU 的时间，不包括阻塞等待 I/O 的时间；响应时间强调“第一次被服务”有多快，适合交互系统。
\end{formula}

\paragraph{先来先服务（FCFS）。} 按到达顺序服务，非抢占。实现简单，但会出现护航效应：一个长 CPU 作业排在前面，后面的短作业和 I/O 作业都要等，CPU 和 I/O 设备可能交替空闲。

\paragraph{短作业优先（SJF）。} 每次选运行时间最短的作业，非抢占。在所有作业同时可用的前提下，SJF 使平均等待时间最短；但长作业可能一直排不上，发生饥饿。实际系统无法预知运行时间，只能用历史数据做指数平均来预测。

\paragraph{最短剩余时间优先（SRTF）。} SJF 的抢占版：新作业到达时，如果它的运行时间比当前进程的剩余时间还短，就抢占 CPU。它能使平均等待/周转时间更短，但调度更频繁，长作业同样可能饥饿。

\paragraph{高响应比优先（HRRN）。} 非抢占，每次选响应比最大的作业：
\[
R=\frac{\text{等待时间}+\text{要求服务时间}}{\text{要求服务时间}}
=1+\frac{\text{等待时间}}{\text{要求服务时间}}.
\]
短作业的 $R$ 天然较大，长作业等待越久 $R$ 也越大，因此兼顾了短作业优先和先来先服务，缓解饥饿。代价是每次调度都要重新计算所有等待作业的响应比。

\paragraph{时间片轮转（RR）。} 就绪队列按 FIFO 排列，每个进程最多运行一个时间片 $q$，用完就放到队尾。$q$ 太大，退化为 FCFS；$q$ 太小，上下文切换的开销占比过高。RR 公平、响应快，适合分时系统，但不区分作业长短，平均周转时间不一定好。

\paragraph{优先级调度。} 每个进程有优先级，可选抢占或非抢占。静态优先级实现简单，但低优先级进程可能饥饿；动态优先级可以根据等待时间调整，老化（aging）就是每等一段时间提高优先级。

\paragraph{多级队列与多级反馈队列。} 多级队列把就绪进程分到几个固定队列，队列之间优先级固定，队列内部可以 RR；进程一般不跨队列，低优先级队列可能饥饿。多级反馈队列允许进程在队列之间移动：新进程进最高优先级队列，时间片用完就降级，低优先级队列的时间片更长；定期把所有进程提升回高优先级队列，防止饥饿。它不需要预知运行时间，能近似短作业优先，是通用操作系统中很常用的一类策略。

\subsection{同步与互斥}

先看一个最简单的竞争例子。两个进程共享一个全局变量 \texttt{count}，都执行 \texttt{count++}。机器级上这不是一条指令，而是“读 \texttt{count} 到寄存器、加 1、写回内存”三步。如果进程 $P_1$ 读到 0 后被切换，$P_2$ 也读到 0，各自加 1 写回，最后 \texttt{count} 还是 1，一次更新丢了。这类错误取决于执行时序，称为竞态条件（race condition）。

访问共享资源的代码段称为\textbf{临界区}。进程进入临界区前要申请许可，离开时释放：

\begin{lstlisting}[language=C]
while (1) {
    entry_section();      // 申请进入
    critical_section();   // 访问共享资源
    exit_section();       // 释放
    remainder_section();  // 其余工作
}
\end{lstlisting}

一个好的临界区管理方案要满足四条：空闲让进（没有进程在临界区时，申请者应能进入）、忙则等待（已有进程在临界区时，其他进程必须等待）、有限等待（申请者不能无限期等待）、让权等待（进不去时应阻塞让出 CPU，而不是忙等）。前三条保证正确性，第四条是效率要求；自旋锁不满足让权等待，但仍然可以是正确的。

\paragraph{Peterson 算法。} 两个进程的软件互斥方案，共享 \texttt{flag[2]} 和 \texttt{turn}：

\begin{lstlisting}[language=C]
bool flag[2] = {false, false};
int turn = 0;
// 进程 i，另一个进程 j = 1 - i
flag[i] = true;       // 我想进
turn = j;             // 如果对方也想进，先让对方进
while (flag[j] && turn == j) ;   // 忙等
/* critical section */
flag[i] = false;      // 我退出
\end{lstlisting}

\texttt{flag[i]} 表示进程 $i$ 想进入，\texttt{turn} 用来在双方同时想进时决定谁先进。只要对方不想进，或者 \texttt{turn} 指向自己，就可以进入；离开时把自己的 \texttt{flag} 置假。它满足互斥、空闲让进和有限等待，但等待方式是忙等，不满足让权等待。考试模型默认顺序一致性；真实多核上还需要内存屏障，这里不展开。

\paragraph{硬件原子指令。} \texttt{TestAndSet} 返回锁的旧值并把锁置为 \texttt{true}，整个过程不可分割：

\begin{lstlisting}[language=C]
bool TestAndSet(bool *lock) {
    bool old = *lock;
    *lock = true;
    return old;
}
// 加锁
while (TestAndSet(&lock)) ;
/* critical section */
*lock = false;
\end{lstlisting}

\texttt{Swap} 或 \texttt{Exchange} 把 \texttt{lock} 和局部变量 \texttt{key} 交换，也能构造自旋锁。原子指令适合多核、临界区很短的场景；等待时间长时，自旋会白烧 CPU，应该阻塞。关中断是单处理器内核保护极短临界区的办法：关中断期间不会被切换，但用户进程不能用它，多处理器上关一个核的中断也挡不住其他核。

\paragraph{信号量。} 信号量是一个只能通过 $P$、$V$ 操作访问的整数。记录型信号量还带一个等待队列，图~2-7 画出了 $P$、$V$ 对值和队列的影响。

\begin{lstlisting}[language=C]
// P(S)：申请一个资源
P(S) {
    S.value--;
    if (S.value < 0) block(S.queue);   // 没有资源，阻塞并排队
}
// V(S)：释放一个资源
V(S) {
    S.value++;
    if (S.value <= 0) wakeup(S.queue); // 队列里还有人，唤醒队首
}
\end{lstlisting}

初值 1 表示有一个资源。$P_1$ 执行 $P$ 后值变为 0，顺利进入；$P_2$、$P_3$ 再执行 $P$，值依次变为 $-1$、$-2$，它们被阻塞并按顺序排队。此时 $|S.value|=2$ 正好是等待进程数。$P_1$ 执行 $V$ 后值从 $-2$ 变到 $-1$，仍然小于等于 0，说明队列里还有人，于是唤醒队首 $P_2$；$P_3$ 继续等待。如果 $V$ 后值变成正数，说明没有等待者，资源重新可用。

因此，记录型信号量满足 $S.value>0$ 时表示可用资源数；$S.value=0$ 时没有可用资源且没有等待者；$S.value<0$ 时 $|S.value|$ 是等待队列长度。$P$ 可能阻塞，$V$ 不会阻塞；$P$、$V$ 本身必须原子执行。

\paragraph{用信号量实现互斥与同步。} 互斥信号量初值为 1，进入临界区前 $P$，离开后 $V$：

\begin{lstlisting}[language=C]
semaphore mutex = 1;
P(mutex);
/* critical section */
V(mutex);
\end{lstlisting}

同步信号量初值为 0，用来约束先后次序。若要求“$A$ 做完某件事后 $B$ 才能做”，就让 $A$ 在事后执行 $V(S)$，$B$ 在事前执行 $P(S)$。$B$ 先跑到 $P(S)$ 时会阻塞，直到 $A$ 发出 $V$。互斥量的 $P/V$ 通常由同一进程成对执行；同步信号量的 $P/V$ 则分属不同进程。

\subsection{经典同步问题}

\paragraph{生产者-消费者。} 有界缓冲区容量为 $N$，生产者放数据，消费者取数据。需要三个信号量：\texttt{empty} 表示空位数，初值 $N$；\texttt{full} 表示数据个数，初值 0；\texttt{mutex} 保护缓冲区的读写指针和内容，初值 1。

\begin{lstlisting}[language=C]
semaphore empty = N, full = 0, mutex = 1;

Producer() {
    while (1) {
        item = produce();
        P(empty);          // 先确认有空位
        P(mutex);          // 再锁住缓冲区
        put(item);
        V(mutex);
        V(full);           // 数据数加 1
    }
}

Consumer() {
    while (1) {
        P(full);           // 先确认有数据
        P(mutex);
        item = get();
        V(mutex);
        V(empty);          // 空位数加 1
        consume(item);
    }
}
\end{lstlisting}

这段代码的关键是 $P$ 的顺序：必须先 $P(empty)$ 或 $P(full)$，再 $P(mutex)$。如果生产者先拿到 \texttt{mutex}，再在 \texttt{empty} 上阻塞，那么缓冲区满时它占着锁睡觉；消费者要取数据也得先拿 \texttt{mutex}，于是消费者也被阻塞，双方互相等待，形成死锁。$V$ 的顺序通常先 $V(mutex)$ 再 $V(full)$ 或 $V(empty)$：先释放锁，再唤醒对方，被唤醒的进程可以立刻进入临界区，减少一次无谓的阻塞。反过来写不影响正确性，但效率略差。

\paragraph{读者-写者。} 多个读者可以同时读，读者和写者不能同时访问，写者和写者也不能同时访问。用 \texttt{readcount} 记录当前读者数，\texttt{mutex} 保护 \texttt{readcount}，\texttt{rw} 保护文件：

\begin{lstlisting}[language=C]
semaphore mutex = 1, rw = 1;
int readcount = 0;

Reader() {
    P(mutex);
    readcount++;
    if (readcount == 1) P(rw);   // 第一个读者锁住文件
    V(mutex);
    read();
    P(mutex);
    readcount--;
    if (readcount == 0) V(rw);   // 最后一个读者释放文件
    V(mutex);
}

Writer() {
    P(rw);
    write();
    V(rw);
}
\end{lstlisting}

第一个读者负责加锁，最后一个读者负责解锁，中间的读者只改 \texttt{readcount}。这样读者之间可以并行，写者必须等所有读者离开。这个版本是读者优先：只要不断有读者到达，写者可能一直等下去。写者优先需要额外的信号量，在写者到达时阻止新读者进入；实现更复杂，也可能让读者饥饿。

\paragraph{管程。} 管程把共享变量和操作这些变量的过程封装在一起，保证同一时刻只有一个进程在管程内执行，互斥由编译器或运行时自动保证，不需要程序员手写 $P/V$。条件变量用于等待某个条件成立：\texttt{wait} 释放管程锁并阻塞，\texttt{signal} 唤醒一个等待者。条件变量不是信号量，它没有计数值；如果 \texttt{signal} 时没有等待者，这个信号就丢失了，不像 $V$ 操作会把值加 1。Hoare 语义下 \texttt{signal} 立即把管程交给被唤醒者；Mesa 语义下被唤醒者只是转入就绪，等当前进程退出管程后再竞争。Java 的 \texttt{synchronized} 和 \texttt{wait/notify} 就是管程风格的同步。

\subsection{死锁}

死锁（deadlock）是指一组进程中的每个进程都在等待一个只能由组内其他进程释放的资源，没有外力介入，谁也无法继续。比如 $P_1$ 占着打印机、等扫描仪，$P_2$ 占着扫描仪、等打印机，双方都不肯先释放。

死锁同时满足四个必要条件：

\begin{enumerate}
  \item \textbf{互斥}：资源一次只能被一个进程使用；
  \item \textbf{请求并保持}：进程已经占有一些资源，又提出新的请求，且不释放已占有的资源；
  \item \textbf{不可剥夺}：资源只能由占有者主动释放，不能被强行抢走；
  \item \textbf{循环等待}：存在一个进程-资源的环形等待链。
\end{enumerate}

这四个条件缺一不可，但同时成立也不一定真的死锁（多实例资源下尤其如此）。图~2-9 用资源分配图画出了两种情形。圆圈表示进程，方框表示资源，方框里的点表示实例；请求边从进程指向资源，分配边从资源指向进程（图中用虚线）。

\paragraph{死锁处理策略。} 表~2-2 概括了四类做法。

\begin{tablebox}{表 2-2\quad 死锁的四种处理策略}
\centering
\begin{tabular}{lll}
\toprule
策略 & 发生时机 & 典型做法 \\
\midrule
预防 & 设计阶段，静态 & 破坏四个必要条件之一 \\
避免 & 每次分配前，动态 & 银行家算法，检查是否仍安全 \\
检测 & 运行过程中 & 资源分配图化简、等待图找环 \\
恢复 & 检测到死锁后 & 终止进程或剥夺资源 \\
\bottomrule
\end{tabular}
\end{tablebox}

\paragraph{预防。} 破坏互斥：把独占设备改造成共享服务，例如打印机假脱机，但很多资源无法这样改造。破坏请求并保持：进程运行前一次申请全部资源，或者申请新资源前先释放已占有的资源；前者资源利用率低，后者可能反复申请释放。破坏不可剥夺：允许抢占资源，被抢的进程回滚到安全点；CPU 和内存容易抢占，打印机这类设备很难。破坏循环等待：给资源编号，进程只能按编号递增的顺序申请，这样不会形成环；代价是资源申请顺序受限，可能产生不必要的等待。

\paragraph{避免。} 不破坏条件，而是在每次分配前判断“分配后系统是否还安全”。安全状态是指存在一个安全序列，按这个顺序每个进程都能获得它声明的最大需求并完成。安全状态一定不会死锁；不安全状态只是可能死锁，因为进程实际请求的资源可能小于它的最大需求。银行家算法就是做这个判断。

设系统有 $n$ 个进程、$m$ 类资源，记录：
\[
Available[j]\ \text{为当前可用的 }j\text{ 类资源数},\quad
Need[i][j]=Max[i][j]-Allocation[i][j].
\]
安全性检查的流程如图~2-10。

从 $Work=Available$ 开始，反复找需求不超过当前可用资源的未完成进程；找到就假设它完成，把已分配给它的资源归还到 $Work$，再继续找。如果所有进程都能完成，系统安全，这个顺序就是一个安全序列；如果还有进程未完成却找不到可推进的进程，系统不安全。安全序列通常不唯一，找到一个即可。

真正分配时，还要先检查请求是否合法：$Request_i\le Need_i$ 且 $Request_i\le Available$。然后做一次试分配，修改 $Available$、$Allocation_i$、$Need_i$，再跑一遍安全性检查；安全才确认分配，不安全就回滚，让进程等待。银行家算法要求每个进程预先声明最大需求，这个条件在实际系统中很难满足，所以它更多用于理论分析和批处理场景。

\paragraph{检测与恢复。} 单实例资源可以用等待图：把资源结点去掉，若 $P_i$ 等待 $P_j$ 占有的资源，就画一条 $P_i\to P_j$ 的边；图中有环就是死锁。多实例资源仍用资源分配图化简。检测本身有开销：太频繁浪费 CPU，太稀疏则死锁进程长期占着资源。

恢复有两种思路。终止进程：可以一次终止所有死锁进程，简单但损失大；也可以逐个终止，直到死锁解除，代价是每次都要重新检测。剥夺资源：从某些进程手中抢走资源，分配给死锁进程，被抢的进程回滚到之前的安全点。选择牺牲者时要考虑已运行时间、还需要的资源、回滚代价，并防止同一个进程反复被选中而饥饿。

\paragraph{死锁、饥饿与活锁。} 死锁一定有循环等待，组内所有进程都无法推进；饥饿没有环，进程只是长期得不到资源，系统其他部分仍在运行，理论上还有机会；活锁是进程不断重试、状态一直在变，但没有实际进展，例如两个进程反复检测到冲突后同时退让。三者都可能表现为“程序不动了”，但原因和处理方式不同。

\subsection{几个容易混淆的判断}

\begin{itemize}
  \item \textbf{阻塞与挂起。} 阻塞是进程在内存中等待某个事件，事件发生就转就绪；挂起是进程被换到外存，即使事件发生，也要先激活换回内存。就绪挂起的进程不参加调度。
  \item \textbf{死锁与饥饿。} 死锁是循环等待，组内进程永远无法推进；饥饿没有循环，只是优先级或资源分配策略导致某个进程长期得不到服务。死锁必须破坏环或剥夺资源，饥饿可以用老化缓解。
  \item \textbf{互斥与同步。} 互斥是“同一时刻只能有一个进程访问”，同步是“按某种先后次序执行”。互斥可以看作同步的一种特例；生产者-消费者既需要互斥（缓冲区），也需要同步（空位和数据个数）。
  \item \textbf{用户级线程的阻塞。} 在多对一模型中，一个线程执行阻塞系统调用，内核按进程阻塞，整个进程都停下；一对一或多对多模型中，其他线程可能继续运行。判断这类题必须先看映射模型。
  \item \textbf{时间片 $q$ 的取舍。} $q$ 太大，RR 退化为 FCFS；$q$ 太小，上下文切换开销占比过高。$q$ 通常取略大于一次典型交互所需的时间。
  \item \textbf{$P/V$ 的顺序。} 互斥场景先 $P$ 资源信号量、再 $P$ 互斥量；颠倒后可能占着锁阻塞，形成死锁。$V$ 的顺序通常先释放互斥量，再唤醒等待者。
  \item \textbf{不安全不等于死锁。} 银行家算法判定不安全，只说明按最大需求继续分配可能进入死锁；进程实际请求较小，系统仍可能顺利完成。安全状态则一定不会死锁。
  \item \textbf{进程切换与线程切换。} 线程切换要保存/恢复寄存器和栈，但同一进程的线程共享地址空间，不需要切换页表；进程切换通常还要换页表并处理 TLB，开销更大。
\end{itemize}
